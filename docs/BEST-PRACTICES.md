# Operational & Security Best Practices

Practices for running the AFIP invoicing CLI safely in production. This complements the
architecture docs — it assumes you already know what `python -m factura <proyecto> <pago#>`
does and focuses on how to run it without hurting yourself.

Electronic comprobantes are legal fiscal documents. Treat every non-`--dry-run`,
non-`--homo` run as an irreversible action against the tax agency (AFIP/ARCA).

---

## 1. Certificate & key handling

**Where things live.** All cryptographic material lives *outside* the repository, in the
user home directory:

| File | Purpose |
|------|---------|
| `~/.afip/clave_privada.key` | RSA-2048 private key (generated by `python -m factura setup-cert`) |
| `~/.afip/solicitud.csr` | CSR uploaded to the ARCA portal |
| `~/.afip/certificado.crt` | Certificate issued by ARCA, bound to the `wsfe` service |
| `~/.afip/token_cache.json` | Cached WSAA token + sign (bearer-equivalent, up to 12 h) |

The paths are configured under the `certificado:` block in `factura-config.yaml`
(`key_path` / `crt_path`, `~` is expanded).

**Never commit any of these.** The repo's `.gitignore` excludes `.afip/`, but that only
matters if you ever place the directory inside the tree — don't. Keep it in `$HOME`,
where the tool expects it.

**Filesystem permissions.** The private key and the token cache are equivalent to your
fiscal identity. Restrict them to your user:

- Linux/macOS: `chmod 600 ~/.afip/clave_privada.key ~/.afip/token_cache.json` and
  `chmod 700 ~/.afip`.
- Windows: keep `%USERPROFILE%\.afip` on a profile only your account can read; check
  with `icacls` that no broad groups (Everyone, Users) have access.

Remember that `token_cache.json` holds a plaintext token+sign pair valid for up to 12
hours (`authenticate()` reuses it with a 5-minute expiry margin). Anyone who copies that
file can call WSFE as you until it expires. If you suspect exposure, delete the file —
the next run re-authenticates from the certificate.

**Rotation / renewal.** AFIP certificates expire (typically ~2 years). The tool
validates on every token-cache **miss**: when a fresh WSAA login is needed,
`validate_certificate()` checks that the certificate has not expired and that the
private key matches the certificate's public key, and aborts with a clear message if
either fails. While a cached token is valid (up to ~12 h), `authenticate()` returns it
directly and skips this check — a cert that expires or is swapped mid-window is not
detected until the cache lapses. Do not wait for that failure:

1. Note the expiry printed on each fresh WSAA login (`Cert valid until: ...`).
2. Well before expiry, run `python -m factura setup-cert` to generate a new key + CSR
   (it prompts before overwriting an existing key), upload the CSR in the ARCA portal,
   and download the new `.crt` to `~/.afip/certificado.crt`.
3. Delete `~/.afip/token_cache.json` so the next run authenticates with the new pair.

**Homologación vs producción certificates are distinct.** A certificate enrolled for
the production environment does not authenticate against the homologación WSAA
(`wsaahomo.afip.gov.ar`) and vice versa — they are separate enrollments in separate
environments. The token cache keys entries as `{service}_{ambiente}`
(e.g. `wsfe_homologacion`, `wsfe_produccion`), so tokens never cross environments, but
the certificate on disk is a single pair: if you actively test against homologación,
keep the homologación material separate and point `factura-config.yaml` at the right
files before switching.

## 2. Safe emission workflow

There is **no `--prod` flag**: with `ambiente: "produccion"` in `factura-config.yaml`, a
bare `python -m factura acme 1` emits a real fiscal document. The only opt-in safety
valves are `--dry-run` and `--homo`. Build the habit accordingly:

```
# 1. Always dry-run first — zero AFIP contact, PDF watermarked "BORRADOR (SIN CAE)"
python -m factura acme 1 --dry-run

# 2. Open the generated PDF and review EVERYTHING:
#    receptor razón social + CUIT, tipo de comprobante, concepto,
#    importe, moneda + cotización, período de servicio, vencimiento de pago.

# 3. Only then emit for real
python -m factura acme 1
```

- **Anything experimental goes to homologación.** New comprobante types, FCE
  (`--tipo 211`), first NC, a new client's billing block, a dependency upgrade — test it
  with `--homo` first. Homologación exercises the full WSAA + WSFE path against AFIP's
  test endpoints and produces no binding documents.
  **Warning — a `--homo` run still writes the ledger.** A live `--homo` run executes
  the same flow as production and records the same `{slug}-{pago}` key in
  `invoices.yaml`; the ledger entry stores no ambiente field. After a homo test of
  `acme 1`, a subsequent production run of `acme 1` prints `*** YA EMITIDO ***` and
  exits 0 — the only way to unblock it is hand-deleting the homo entry, which the
  hand-edit rule below otherwise forbids. Run homo tests against a slug/pago you will
  never emit in production.
- **A dry-run is not a homologación test.** `--dry-run` never touches AFIP, so it
  validates your data and the PDF, but not what AFIP will accept. For structural changes
  you need both: `--dry-run` to review, `--homo` to validate against the service.
- **Never edit `invoices.yaml` by hand.** It is the idempotency source of truth:
  `check_already_emitted()` decides whether a run proceeds based solely on the presence
  of the `{slug}-{pago}` key. A hand-added entry silently blocks a legitimate emission;
  a hand-deleted one allows a duplicate comprobante. The code neither produces nor
  understands ad-hoc fields — if you need to annotate an anomaly, do it somewhere else
  (a separate notes file), not inside the ledger.
- **Back up `invoices.yaml`.** Besides AFIP's own records, it is your only local record
  of what was emitted (comprobante number, CAE, amount, date, filename). It is also
  rewritten in full on every save with no locking or backup copy, so a crash mid-write
  can lose it. Keep it in your regular backup rotation and snapshot it before any bulk
  operation.
- Re-running an already-emitted invoice is safe: the tool prints `*** YA EMITIDO ***`
  with the comprobante/CAE/date/file and exits 0.

## 3. Idempotency discipline

**What the ledger protects against:**

- Double emission from an accidental re-run: the `{slug}-{pago}` key check exits before
  any AFIP call.
- Double credit notes: `--nc` requires the *original* entry to exist and refuses if the
  `{slug}-{pago}-nc` key is already present.
- Losing track of what was emitted: every live emission records comprobante, tipo, CAE,
  CAE expiry, amount, currency, cotización, concepto, filename and emission date.

**What it does NOT protect against:**

- **Another machine.** The ledger is a local YAML file; there is no shared state and no
  AFIP-side check before emission. If you run the tool from a second machine (or a
  restored backup) whose `invoices.yaml` is stale, nothing stops a duplicate
  comprobante. This tool has a **single-machine assumption** — pick one machine as the
  emission host and only emit from there. If you must migrate, copy `invoices.yaml`
  (and `factura/audit.log`) first, and verify against AFIP with
  `FECompUltimoAutorizado` before the first emission on the new host.
- **Concurrent runs.** `save_ledger()` rewrites the whole file with no lock. Never run
  two emissions in parallel.
- **A crash between CAE and ledger write.** In the live flow, `record_invoice()` runs
  *after* `solicitar_cae()` and PDF generation — see section 6.
- **Payment renumbering.** The key is `{slug}-{pago}`; if you renumber payments in the
  external projects registry, the ledger keys no longer mean what they did. Don't
  renumber payments that have emitted invoices.

## 4. Audit log

`factura/audit.log` is an append-only trail written by `append_audit_log()`. A line is
appended only when a run **completes** its flow (the call sits at the end of the dry-run,
live and NC paths), with one of four events:

```
DRY_RUN     — dry-run of a factura (no ledger write)
DRY_RUN_NC  — dry-run of a nota de crédito
EMITIDA     — live factura (also written to the ledger)
NC_EMITIDA  — live nota de crédito (ledger entry with -nc suffix)
```

Runs that exit early leave **no** line: `*** YA EMITIDO ***` idempotent re-runs,
config/registry/payment lookup errors, AFIP rejections (the tool exits inside the WSFE
error handling), and any crash between the CAE grant and the audit write. Failed and
idempotent runs are therefore invisible in the log.

Practices:

- **Review it after each run**, especially live ones: confirm the `EMITIDA` line matches
  what you intended (slug, pago, cbte, cae, monto, `ambiente=`). A quick
  `tail factura/audit.log` is enough.
- The `ambiente=` field is your fastest check that a test didn't accidentally run
  against production.
- **Keep it with your backups.** It is gitignored (local only) and it is the only place
  where dry-runs are recorded — useful when reconstructing "what did I run that day",
  with the caveat above: it only shows runs that completed, not failed or blocked
  attempts. Back it up alongside `invoices.yaml`.
- Never edit or truncate it. If it grows large, archive a copy and let it keep
  appending; do not rewrite history.

## 5. Config hygiene

The repository should never contain real fiscal or client data. Three untracked files
hold most of it:

| File | Contains | Git status |
|------|----------|------------|
| `factura-config.yaml` | Your CUIT, legal name, domicilio, punto de venta, CBU/alias | must stay **untracked** |
| `invoices.yaml` | Client slugs, amounts, CAE numbers | must stay **untracked** |
| `factura/audit.log` | Client slugs, amounts, CAEs, environments | already gitignored |

Plus the external projects registry referenced by `registry_path` — it lives outside the
tool entirely and is consumed strictly read-only; never copy it into the repo.

**The published source contains only placeholder data** — CUIT `20123456789`, name
`Perez Juan`, client slugs `acme` / `globex`. If you fork this repo and put your own
identifiers into help text, constants, examples, or docs while adapting it, scrub them
before sharing the source again.

Rules:

- `.gitignore` already excludes `factura-config.yaml` and `invoices.yaml` (alongside
  `.afip/`, `*.pdf`, `__pycache__/`, `factura/audit.log`) — keep it that way.
- **Commit only `*.example.yaml` files** with placeholder data: CUIT `20123456789`
  (format 20-12345678-9), name `Perez Juan`, CBU `0000000000000000000000`, alias
  `MI.ALIAS.CBU`, client slugs like `acme` / `globex`. The repo ships
  `factura-config.example.yaml`, `projects-registry.example.yaml` and
  `invoices.example.yaml`; set up a new machine by copying
  `factura-config.example.yaml` → `factura-config.yaml` and filling in real values
  locally.
- Generated PDFs embed your CUIT in the filename
  (`{cuit}_{tipo:03d}_{pv:05d}_{nro:08d}.pdf`); `*.pdf` is gitignored, keep it that way.
- `.gitignore` protects the git repo, not a zip or a folder copy. Before sharing the
  tree by any other channel, remove the data files (`factura-config.yaml`,
  `invoices.yaml`, `factura/audit.log`) and `__pycache__/` (compiled `.pyc` files embed
  string constants from the sources).

## 6. Error recovery

The live flow order is: WSAA auth → `get_ultimo_autorizado()` → `solicitar_cae()` →
PDF generation → `record_invoice()` → audit log. Failures behave very differently
depending on where they happen.

**Failure before or during `solicitar_cae()` (auth error, network drop, AFIP rejection).**
If AFIP rejected the request (`Resultado != 'A'`), the tool exits printing the AFIP
`Observaciones` codes — fix the cause and re-run; nothing was emitted. If the call
failed *ambiguously* (timeout, connection reset mid-call), do **not** blindly retry:
AFIP may have authorized the comprobante even though you never saw the response.
Check first:

1. Query the last authorized number for that type and punto de venta
   (`FECompUltimoAutorizado` — the same call the tool makes in every **live** run;
   `--dry-run` never contacts AFIP — `WSFEClient.get_ultimo_autorizado()`).
2. Compare it with the "Último: N, Próximo: N+1" the tool printed before the failure.
   If the last authorized number *advanced*, AFIP granted a CAE you don't have locally.
3. Retrieve the comprobante's details with `FECompConsultar`. The client method exists
   (`WSFEClient.consultar_comprobante(punto_venta, tipo_cbte, cbte_nro)` in
   `factura/afip_wsfe.py`) but is **not wired into the CLI** — call it from a short
   Python snippet or the REPL after authenticating.

**CAE granted but PDF/ledger write failed** (e.g. WeasyPrint missing, disk error after
`solicitar_cae()` succeeded). This is the dangerous window: the comprobante exists at
AFIP, but `invoices.yaml` has no entry, so a naive re-run would emit a **second, duplicate
comprobante**. Recovery:

1. Get the CAE, CAE expiry and amounts from the terminal output of the failed run
   (they are printed before PDF generation), or recover them via `FECompConsultar` as
   above.
2. Manually add the ledger entry to `invoices.yaml` mirroring exactly what
   `record_invoice()` would have written (`comprobante`, `tipo`, `cae`, `cae_vto` as
   `YYYY-MM-DD`, `monto`, `moneda`, `cotizacion`, `concepto`, `filename`, `emitted` as
   the real emission date in ISO format). This is the **one sanctioned exception** to
   the "never hand-edit the ledger" rule — you are reconstructing what the code failed
   to write, not inventing state. Match the schema exactly; use the `emitted` date the
   comprobante was actually authorized (it feeds the NC `CbtesAsoc` date and the annual
   total).
3. Regenerate the PDF if needed (fix the underlying issue first — e.g. WeasyPrint
   install — then confirm the render pipeline with a `--dry-run` of a **different,
   not-yet-emitted** payment, or run it before adding the ledger entry in step 2: the
   idempotency check runs before the dry-run branch, so a `--dry-run` of the recovered
   slug+pago just prints `*** YA EMITIDO ***` and exits without rendering anything; the
   fiscal document is the AFIP record, the PDF is a representation).
4. Only after the ledger entry exists, resume normal operation. Verify with a re-run:
   it must print `*** YA EMITIDO ***`.

**General rule:** when in doubt, ask AFIP what it thinks before re-running. AFIP's
records are authoritative; the ledger is a local mirror.

## 7. Legal / compliance notes

- **A comprobante with a CAE is a legally binding fiscal document.** Once
  `FECAESolicitar` returns `Resultado: A`, the invoice exists in AFIP's records
  regardless of what happens on your machine. There is no "undo", no deletion, no
  editing.
- **The Nota de Crédito is the only correction mechanism.** Wrong amount, wrong
  receptor, wrong concepto → emit an NC against the original (`--nc`; the tool maps
  tipo 11 → 13 and 211 → 213 and links the original via `CbtesAsoc`), then emit a
  corrected factura. Never "fix" a mistake by deleting a ledger entry or ignoring an
  emitted comprobante — the AFIP record stands either way.
- **Never delete emitted documents.** Keep every generated PDF, the ledger and the
  audit log. Argentine tax law requires retaining invoicing documentation for the full
  statute of limitations on tax obligations — commonly interpreted as **10 years**.
  Design your backups around that horizon, not around convenience.
- **Currency compliance.** USD invoices must use the official BNA (vendedor) exchange
  rate per RG 4291/2018 — not MEP/blue/CCL. The tool does this by default (live mode
  takes the rate from AFIP's own `FEParamGetCotizacion`). The `--cotizacion` override
  exists for legitimate contractual cases; if you use it, be sure the rate is
  defensible and document why.
- **Monotributo caps.** The annual summary printed after each completed factura run
  (dry-run or live — Nota de Crédito runs and early exits don't print it) compares your
  year-to-date billing against hardcoded category caps in `factura/cli.py`
  (`_print_annual_summary()`, marked "2025/2026 approximate"). Treat it as a heads-up,
  not as compliance: verify the current official caps each fiscal year and update the
  constants, and confirm your recategorization status with your accountant when the
  warning fires (>80% — checked against the category H cap only).
- **Homologación output is not fiscal.** Documents emitted with `--homo` have no legal
  validity — but also never present a homologación PDF to a client as if it were real;
  check `ambiente=` in the audit log if unsure which environment produced a file.
